# Публичная CRM для жюри

Третий пункт сдачи — доступный из интернета адрес работающей CRM и учётные записи проверяющих. Репозиторий, презентация и localhost этот адрес не заменяют. Публикация пока не выполнена: сервер и доменные имена не предоставлены.

## Что необходимо

- Linux-сервер с Docker Engine и Compose 2.24.4+; ориентир для демонстрации — 4 CPU, 8 ГБ RAM и 20 ГБ диска.
- Два DNS-имени, например `crm.example.org` и `auth.example.org`, направленные A-записями на IP сервера. Это примеры, не действующие адреса проекта. Если есть AAAA-записи, они тоже должны вести на этот сервер.
- Входящие TCP 80/443 и SSH для администратора; наружу публикуется только HTTPS-прокси. PostgreSQL, Redis, API и Keycloak доступны внутри сети Compose.

## Подготовка на сервере

Скопируйте исходники, установите Python 3 и выполните из корня, указав свои имена:

```bash
python3 scripts/prepare_public.py --crm-domain crm.example.org --auth-domain auth.example.org
docker compose --env-file .env.public -f docker-compose.yml -f docker-compose.public.yml config --quiet
docker compose --env-file .env.public -f docker-compose.yml -f docker-compose.public.yml up --build -d --wait --wait-timeout 600
```

Сценарий создаёт уникальные пароли всех семи демопользователей и системного администратора, настройки redirect URI / CORS / issuer и отдельный импорт realm. `.env.public` и `.deployment/` исключены из Git и Docker build context. Не публикуйте их и не отправляйте в чат. Сценарий отказывается перезаписывать существующие секреты. Он рассчитан на **первый запуск с пустыми public-volumes**; realm import не меняет пароли существующих пользователей. Volumes локального проекта отделены именем `it-school-crm-public`.

Caddy получает и обновляет TLS-сертификаты автоматически при корректном DNS и доступных 80/443. Keycloak запускается командой `start` за HTTPS-прокси. Его административные URL не публикуются; управление возможно через `kcadm.sh` внутри контейнера. Это конфигурация демонстрационного стенда с синтетическими данными, не заявление полного нормативного соответствия production.

## Проверка перед сдачей

1. `docker compose ... ps`: все сервисы healthy/running. Используйте те же `--env-file` и два `-f`, что выше.
2. Из backend-контейнера запросите `/health`: PostgreSQL и Redis должны быть `ok`.
3. Откройте `https://ВАШ_CRM_ДОМЕН` с телефона через мобильный интернет. Вход должен перенаправлять на ваш auth-домен, не на localhost.
4. Проверьте admin/manager/user, карточку ВУЗа, этап, комментарий, файл, импорт и PDF/XLSX-отчёт. Адреса и пароли — в `.deployment/demo-access.json`.
5. Проверьте повторный запуск контейнеров без потери записей и вложений; не используйте `down -v`.
6. Передайте жюри HTTPS-ссылку и нужные демоаккаунты через закрытые поля платформы. Пароль системного администратора Keycloak не передавайте как демоучётку.

Оставьте сервер работающим на весь период проверки. Публичный запуск этой конфигурации пока не выполнялся; локальная проверка `config` не заменяет проверку на сервере.

Документация: [Keycloak reverse proxy](https://www.keycloak.org/server/reverseproxy), [Caddy Automatic HTTPS](https://caddyserver.com/docs/automatic-https).
